## 1. Layer Norm 为什么可以在 Sequence 维度分开处理

Layer Norm 的统计量（均值、方差）**只在 Hidden 维度 $D$ 上计算**，与其他位置的 token 完全无关：

$$\mu_{b,t} = \frac{1}{D}\sum_{d=1}^{D} x_{b,t,d}, \quad \sigma_{b,t} = \sqrt{\frac{1}{D}\sum_{d=1}^{D}(x_{b,t,d} - \mu_{b,t})^2 + \epsilon}$$

**结论**：每个 token 的 LayerNorm 计算彼此独立，可以任意切分 sequence 维度并行处理，无需跨位置通信。

| Norm 类型 | 统计量计算轴 | 能否在 Sequence 上分开？ |
|---|---|---|
| Layer Norm | Hidden dim $D$ | ✅ 可以 |
| Batch Norm | Batch + Sequence | ❌ 不能 |
| RMS Norm | Hidden dim $D$ | ✅ 可以 |

## 2. 三种并行方式

### 2.1 张量并行（Tensor Parallelism, TP）

- **切分粒度**：单层内部的权重矩阵
- **通信模式**：每次矩阵乘法后做 AllReduce，**通信与计算强耦合**
- **要求**：必须使用高带宽互联（NVLink ~600GB/s），**只能在单机内使用**
- **上限**：TP 度 = 单机 GPU 数（通常为 8）

### 2.2 流水线并行（Pipeline Parallelism, PP）

- **切分粒度**：按层切分模型，每台机器负责若干层
- **通信模式**：层间传递激活值，通信量小，**可以跨机器**
- **缺点**：流水线阶段越多，**bubble（空泡）越多**，GPU 利用率越低
- **缓解方法**：使用 micro-batch 填充 bubble

```
PP=4 时的 bubble 示意：
GPU0: [计算][计算][          bubble          ]
GPU1:        [计算][计算][     bubble        ]
GPU2:               [计算][计算][  bubble    ]
GPU3:                      [计算][计算][bubble]
```

### 2.3 数据并行（Data Parallelism, DP）

- **切分粒度**：切分训练数据，复制完整模型副本
- **通信模式**：每个 step 结束后同步梯度（AllReduce）
- **特点**：模型已能放入显存后，用于继续扩展训练规模

---

## 3. 3D 并行的组合策略

### 核心等式

$$\text{总 GPU 数} = \text{TP} \times \text{PP} \times \text{DP}$$

### 实践经验法则（优先级顺序）

```
第一步：先让模型放进显存
  ├── TP：用满单机 GPU（通常 =8），利用 NVLink 高带宽
  └── PP：跨机器切分层，通信量小可以接受低带宽

第二步：GPU 还有富余
  └── DP：复制副本，处理更多数据
```

### 为什么按此顺序？

| 并行类型 | 通信频率 | 带宽需求 | 分配优先级 |
|---|---|---|---|
| TP | 每次矩阵乘后 | 极高（NVLink） | 最先满足，锁死在单机内 |
| PP | 每层间一次 | 中等（IB可接受） | 其次满足，跨机器扩展 |
| DP | 每个step一次 | 低 | 最后，用剩余GPU填充 |

## 4. 为什么大模型的 DP size 越来越小？

从 Megatron-LM 论文的实验数据可以观察到：

| 模型大小 | TP | PP | GPU总数 | DP |
|---|---|---|---|---|
| 1.7B | 1 | 1 | 32 | **32** |
| 39.1B | 8 | 2 | 512 | **32** |
| 145.6B | 8 | 8 | 1536 | **24** |
| 310.1B | 8 | 16 | 1920 | **15** |
| 1008B | 8 | 64 | 3072 | **6** |

**原因**：
- TP 很快到达上限（=8，单机 GPU 数），无法继续增大
- 模型越大，需要越大的 PP 来装下所有层
- 总 GPU 数增速跟不上 PP 的需求增速
- 因此 DP = 总GPU / (TP × PP) 被持续压缩

> DP 大不是因为它被优先分配，而是小模型不需要太多 TP/PP，GPU 自然溢出给了 DP。模型越大，TP/PP 越贪婪，DP 就越小。

## 5. ZeRO 优化

### 标准 DP 的内存构成

每张 GPU 完整存储（每参数）：

| 内容 | 精度 | 字节/参数 |
|---|---|---|
| 模型参数 | fp16 | 2 |
| 梯度 | fp16 | 2 |
| 优化器状态（参数+momentum+variance） | fp32 | 12 |
| **合计** | | **16** |

### ZeRO Stage 1：切分优化器状态

只将**优化器状态**按 DP 度切分，参数和梯度仍然完整保留：

```
DP=4 时：
GPU 0: 参数(完整) + 梯度(完整) + 优化器状态[0~25%]
GPU 1: 参数(完整) + 梯度(完整) + 优化器状态[25~50%]
GPU 2: 参数(完整) + 梯度(完整) + 优化器状态[50~75%]
GPU 3: 参数(完整) + 梯度(完整) + 优化器状态[75~100%]
```

- 内存节省：优化器状态从 $12N$ → $12N / \text{DP}$ bytes
- 通信变化：AllReduce → Reduce-Scatter + AllGather，**通信量几乎持平**

### ZeRO vs PP+TP 的选择

| | PP + TP | ZeRO-3 |
|---|---|---|
| 思路 | 模型切片，各管一部分 | 参数分片，用时广播 |
| 通信模式 | 点对点，局部 | AllGather，全局 |
| 适合场景 | 集群带宽充足 | 带宽受限但 GPU 多 |
| 缺点 | bubble、实现复杂 | 通信量大 |

> 选哪个取决于集群带宽（BW）——这正是 Megatron 论文中 *"depending on BW"* 的含义。

## 6. 梯度累积

**问题**：DP 小 → 有效 batch size 小 → 梯度同步过于频繁，通信效率低。

**解决**：本地累积多个 micro-batch 的梯度后再同步一次，等效于更大的 batch size，以计算换通信效率。

$$\text{有效 batch size} = \text{micro-batch size} \times \text{梯度累积步数} \times \text{DP}$$
